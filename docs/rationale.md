# Architectural Decision Rationale

Each major decision below states the alternative(s) considered and why the chosen option
fits an enterprise, production, many-users context better.

| Decision | Chosen approach | Alternative(s) considered | Why chosen |
|---|---|---|---|
| **Orchestration surface** | Claude API (Messages API) with a self-hosted manual agent loop | Managed Agents (Anthropic-hosted loop + sandbox); Claude Agent SDK | Managed Agents hosts the tool-execution *sandbox* on Anthropic's infrastructure — a poor fit when every tool needs private-network access to internal systems (wiki index, HR DB, ticketing API) and the enterprise needs the tool-execution layer inside its own VPC, under its own auth/logging/compliance boundary. A self-hosted loop keeps 100% of the data plane in-house; only the "generate next turn" call leaves the network. |
| **Model** | Claude Sonnet 5 as the general-purpose model, Claude Haiku 4.5 for classification/simple-FAQ routing | Claude Opus 5 for everything; a single fixed model | Opus 5 for every request would roughly double per-token cost for a workload where most questions are simple lookups. Sonnet 5's price/performance point (1M context, adaptive thinking, `effort` tuning) fits the general case; a cheap/fast model absorbing the high-volume simple tier keeps average cost per query down without sacrificing quality on hard questions. |
| **Priority Tier / throughput SLA** | Not used for the Sonnet 5 tier; considered only if the org later needs a hard-guaranteed-throughput SLA, in which case that traffic would need to run on a Priority-Tier-eligible model (e.g. Opus 4.8), not Sonnet 5 | Assume Priority Tier is available on the primary model | Priority Tier currently excludes Claude Sonnet 5 and Claude Opus 5. Any SLA design that assumes guaranteed-throughput pricing must pick a model that actually supports it — this is called out explicitly so a later SLA requirement doesn't silently break on model choice. |
| **Extended thinking** | Adaptive thinking always on; `effort` varies per query (low/medium for lookups, high/xhigh for multi-hop synthesis) | Fixed high effort for every query; thinking disabled by default | A fixed high-effort setting wastes cost and latency on the majority-simple query mix. Leaving thinking off entirely (a real option on Opus 5+) risks the model narrating a tool call in visible text instead of a structured tool_use block in edge cases — keeping thinking on and varying only `effort` avoids that failure mode while still controlling cost. |
| **Prompt caching** | Single `cache_control` breakpoint on the system block, 1-hour TTL | No caching; default 5-minute TTL; per-request unique system prompts | The system prompt + tool definitions are identical across all employees and requests — the textbook case for caching. A 5-minute TTL would still catch continuous daytime traffic but wastes cache-write cost on any gap over 5 minutes (lunch breaks, low-traffic hours); the 1-hour variant better matches real usage gaps at the cost of a slightly higher per-write price, and pays for itself at anything above low query volume. |
| **Structured output** | JSON schema (`answer`, `sources`, `confidence`, `escalate`) via `output_config.format` | Free-form text parsed downstream with regex/heuristics | The chat UI, Slack app, and audit log all need the same machine-readable shape. Constraining the schema server-side removes an entire class of "the model almost followed the format" parsing bugs and keeps token usage bounded. |
| **Tool schema strictness** | `strict: true` on all four custom tool definitions | Default (best-effort) schema validation | Three of the four tools touch internal systems (DB, ticketing) where a malformed argument should fail *before* it reaches that system, not after. Strict mode guarantees the input validates against the schema exactly. |
| **Web access** | Anthropic's server-side `web_search` tool, `allowed_domains`-restricted | A custom client-side web-search tool; no web access at all | The server-side tool avoids standing up and maintaining a separate search backend. Restricting `allowed_domains` keeps answers grounded in approved public sources (e.g. a vendor's official docs) rather than the open web, which matters for an internal assistant that should not casually cite arbitrary websites. |
| **Monitoring** | Per-request structured logging of tokens/cache/latency/tool errors, rolled up to dashboards with alerting on cache-hit-rate and cost-spike thresholds | Logging only final answers; cost review as a periodic manual audit | An assistant serving "many users" needs monitoring granular enough to catch a regression (e.g. an accidental system-prompt change breaking the cache) within hours, not at the next monthly bill review. |
